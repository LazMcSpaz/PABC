## What's actually left

### 1. AI quality (engine-adjacent, not new systems)

**Update (2026-08-06):** two of the three gaps below are now closed —
see `docs/ai-overhaul-plan.md` for the full writeup. Contests are now
EV-gated (`ai.js` uses `previewAttackerStrength`/`previewLocationContest`
from `contest.js` + a `winProbability` check tuned by the faction's
aggression dial) and `training-grounds` is no longer a hardcoded id
(chips now carry a generic `unitCapBonus` field; `actions.js` exports
`recruitCapBonus(state, pid)`). Measured on the seed-42 harness AI-vs-AI
smoke test: contest win rate 21% → 87%, captures roughly doubled, and the
game no longer produces one faction's army getting wiped to near-zero.

**Update (2026-08-07):** the Tech Wheel allocator is fixed too. Turned out
the wheel itself was never the gap (see the corrected table row above) —
`maybeAssignTech` was. It picked ONE path by faction dial via a hardcoded
if/else that could literally never produce `"logistics"` (dead branch —
present in the lookup map, never reachable through the conditional), and
filled exactly 3 nodes (entry + one branch) before every later call found
all 3 already assigned and silently did nothing — any Ability Point earned
past that point (a faction can reach 4) was wasted forever. Replaced with
`TECH_NODE_SCORE`, a table of 20 small situational scoring functions (one
per node id — hand-written and bounded is right-sized here since the wheel
is a fixed, engine-owned set of exactly 20 nodes content authors never
extend, unlike chips) plus an additive `techIdentityWeight` that tilts
scores by the faction dial instead of hard-excluding 3 of 4 paths.
Confirmed in a real AI-vs-AI game (seed 777): `plainers` maxed Military's
B-branch, then correctly spent its 4th point on `eco-entry` instead of
losing it — exactly the scenario the old code stranded.

**Still open:**

- **Build (chip) scoring is a hand-tuned heuristic**, not the generic
  effect→value table the overhaul plan calls for. It mostly works today
  because current content sticks to a handful of known fields, but it's not
  robust to new chip effects (movement, influence, vision, detection,
  loyalty-rate chips still score 0 / get ignored in `pickBuild`). The tech
  side of this same concern is now resolved (above) — what's left is
  specifically the *chip* build scorer, which faces the open-ended-content
  problem the tech fix didn't have to.

**Recommended next step:** the full effect→value table rewrite
(`docs/ai-overhaul-plan.md`'s "shared evaluation core") is the remaining
bigger lift, scoped to chip/build scoring now — worth doing once new chip
content starts landing with effect types the current scorer can't see.

**Related hygiene fix, same day:** `recon-team` had the identical
id-hardcode problem as `training-grounds` (three copies of "count chips
with this literal id" — `encounters.js`, and a duplicate in
`Prototype.jsx`'s UI code), for the same underlying mechanic class
(a chip granting an encounter redraw). Generalized the same way: a
`encounterRedraws` schema field, one exported `encounterRedrawBudget(state,
pid)` in `encounters.js` that both the engine and the UI now call instead
of each re-deriving it. Worth grepping for `chipId ===` /
`locationId ===` occasionally — content.js's own header says the engine
never branches on content ids, and two real violations turned up in one
sitting once someone went looking.

### 3. Cleanup

- ~~Remove `src/engine/`, `src/components/`, `src/hooks/`~~ — **done
  (2026-08-06).** 38 files deleted; `npm run build` output identical
  before/after (507 modules, same bundle hash), confirming they were
  never part of the live app.
- **Art assets** — faction emblems, terrain tiles, icons. Still a checkbox
  in the README, unaffected by everything above.
- **Retire/mark-stale the completed planning docs** so future agents (or
  future you) don't re-plan finished work — this pass updates
  `v0.2-implementation-roadmap.md`, `ai-overhaul-plan.md`, and
  `parallel-agent-briefs.md` in place with corrected status banners rather
  than deleting them, since their implementation detail is still accurate
  and useful as history.
- ~~Harness determinism~~ — **done (2026-08-06).** `node src/game/harness.js
  <seed>` failed on roughly 1 in 6 seeds (verified seeds 3, 5, 10, 11, 25, 35,
  41, 123 among others) — not an engine bug, a test-fixture one. Root causes,
  both the same shape (a fixture assumes a specific hex/Location picked by
  "first in iteration order" is a blank slate, which isn't true for every
  seed's procedural map):
  1. Several Phase 3/5/Salvage/Loot combat fixtures staged 1v1 duels on
     "the first terrain-type hex," which can coincide with a faction's
     actual starting unit position, silently adding an uncounted ally to
     one side and throwing off every exact-margin/exact-Strength assertion
     downstream. Fixed with a `clearHexOfUnits` fixture helper.
  2. Three Diplomacy/Influence tests picked "the first neutral Location" to
     capture/integrate/decay and asserted a ZoC-border-size change — true in
     general, but not for every possible Location (one already deep in
     friendly territory has no border left to move). Fixed by asserting the
     claim as an existence check across *all* neutral Locations instead of
     gambling on the first one; the Open-Borders trespass tests were
     similarly fixed by reading the emitted `territory_trespassed` event
     instead of net before/after Standing (a field-encounter tile drawn
     incidentally by the same move can change Standing on its own and mask
     the signal).
  3. The "no vision cheat" fog check assumed `turnOrder[0]` never sees the
     whole (small, 30-hex) map at game start; on some seeds that faction's
     sightlines legitimately cover it. Changed to check the invariant across
     all four factions (fog IS real if *at least one* doesn't see everything
     — verified true on every seed tried).

  Verified clean (0 failures) across a 300+-seed sweep (0–150, 200–350) plus
  the seeds that were failing before. This matters going forward: content
  authors and anyone running `harness.js <seed>` to reproduce a specific bug
  no longer need to wonder whether a red check is real or a fixture fluke.

### 4. Touch / iPad support — done (2026-08-07)

The prototype was mouse-only outside of `BoardViewport`'s pan (which
already used Pointer Events). Added:

- **The tech wheel's tap-to-preview / tap-to-confirm.** `TechWheel.jsx`'s
  `Segment` used to arm its info preview on `onMouseEnter` and assign on
  `onClick`. On a real touch device this broke in a genuinely subtle way,
  not just "no hover exists": mobile Safari/Chrome *synthesize*
  mouseenter→mouseleave→click around every tap (so CSS `:hover` can flash
  and clear), and all three fire in one browser task before React
  re-renders in between — so the synthesized mouseleave un-armed the
  preview before the click handler's own render ever saw it armed. Fixed
  by switching to `onPointerEnter`/`onPointerLeave` filtered to
  `pointerType === "mouse"` (Pointer Events carry the true origin device,
  unlike synthetic MouseEvents) — touch now arms/confirms purely through
  two separate `onClick` calls, which are genuinely separate events.
  Verified live in a real browser (Playwright, iPad viewport + CDP
  multi-touch dispatch, not just code review): tap 1 shows the info strip
  without assigning, tap 2 on the same segment assigns; mouse hover+click
  behavior is unchanged (verified side by side in the same test run).
- **Board pinch-to-zoom.** `BoardViewport.jsx` already panned via unified
  Pointer Events but only zoomed via mouse wheel — unreachable by touch
  (Safari doesn't synthesize `wheel` from a pinch). Added 2-pointer
  tracking to the existing `onPointerDown/Move/Up` handlers: a 2nd finger
  hands off from single-finger pan to pinch (incremental scale + pan
  toward the midpoint each frame, same math family as the existing wheel-
  zoom); lifting to 1 finger resumes panning from wherever it left off
  instead of a dead zone. Mouse is untouched (mouse only ever produces one
  pointer, so the whole branch is unreachable for it). Verified via CDP
  `Input.dispatchTouchEvent` two-finger gestures: pinch-out hit
  `MAX_SCALE`, pinch-in hit `MIN_SCALE`, and a single-finger pan
  immediately after tracked the drag delta exactly.
- **Chip and garrison tooltips** (`Chip.jsx`, `GarrisonValue.jsx`) were
  hover-only with no click-through action at all, so they were simply
  invisible on touch — you couldn't see a chip's effect text on an iPad.
  Added `useTapTooltip` (new shared hook, `kit.jsx`) so tapping toggles the
  same popover hover shows, with tap-outside-to-close (mirrors the
  editor's `HelpTip` tap-popover pattern). Mouse hover is unchanged.
- **`index.html` viewport meta** — added `maximum-scale=1, user-scalable=no`
  so iOS Safari's native double-tap-zoom/pinch-zoom-the-page doesn't fight
  the board's own pinch-zoom or the tech wheel's tap-tap pattern.
- **Deployment** — no work needed here: `.github/workflows/pages.yml`
  already auto-deploys every push to `main` to
  `https://lazmcspaz.github.io/PABC/`, confirmed live via the Actions
  history. That's the URL to test from an iPad — nothing needs to run
  locally.

**Known remaining gap, not yet fixed:** `SalvageModal.jsx`'s chip-pickup
uses HTML5 drag-and-drop (`draggable`, `onDragStart/onDragOver/onDrop`),
which has no equivalent on iOS Safari touch at all — salvage-chip
assignment after a kill will not work on an iPad today. Fixing it means
rewriting that interaction as pointer-based drag (reusing the same
Pointer Events pattern as `BoardViewport`'s pan), not a small tweak —
flagged here rather than done silently since it wasn't explicitly in
scope for this pass.

## Suggested sequencing

Unlike the v0.2 roadmap, these three buckets are **not** dependent on each
other — they can run fully in parallel:

```
AI quality (ai.js only)         ─┐
Content authoring (editor + CSVs) ─┼─► converge whenever, no shared files
Legacy cleanup + art             ─┘
```

- **Content authoring** has the best ratio of "amount left" to "no
  engineering risk" — it's the natural place to put the most hours right
  now, and multiple people can author in parallel (quests, world
  encounters, chips, locations, tuning tables are all independent files/
  tables in the editor).
- **AI EV-gating for contests** is the highest-value engineering fix if you
  want the AI to *feel* smart while content is being authored — small,
  contained to `ai.js` + reading existing `contest.js` math, no schema
  changes.
- **Art** has no dependencies and can happen whenever someone has spare
  time. (Legacy removal — the other item in this bucket — is done.)

## Guardrails (carried over, still apply)

- Never hand-edit `content/` or `src/game/content/` — the editor tool owns
  them; author through it.
- Verify with `node src/game/harness.js` before calling any engine change
  done; it's cheap and catches regressions across every system at once.
- `src/prototype/engineAdapter.js` remains the only seam between the engine
  and the React UI.
