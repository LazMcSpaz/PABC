## What's actually left

### 1. AI quality (engine-adjacent, not new systems)

**Update (2026-08-06):** two of the three gaps below are now closed —
see `docs/ai-overhaul-plan.md` for the full writeup. Contests are now
EV-gated (`ai.js` uses `previewAttackerStrength`/`previewLocationContest`
from `contest.js` + a `winProbability` check tuned by the faction's
aggression dial) and `training-grounds` is no longer a hardcoded id
(chips now carry a generic `unitCapBonus` field; `actions.js` exports
`recruitCapBonus(state, pid)`). Measured on the seed-42 harness AI-vs-AI
smoke test: contest win rate 21% → 87%, captures roughly doubled, and the
game no longer produces one faction's army getting wiped to near-zero.

**Update (2026-08-07):** the Tech Wheel allocator is fixed too. Turned out
the wheel itself was never the gap (see the corrected table row above) —
`maybeAssignTech` was. It picked ONE path by faction dial via a hardcoded
if/else that could literally never produce `"logistics"` (dead branch —
present in the lookup map, never reachable through the conditional), and
filled exactly 3 nodes (entry + one branch) before every later call found
all 3 already assigned and silently did nothing — any Ability Point earned
past that point (a faction can reach 4) was wasted forever. Replaced with
`TECH_NODE_SCORE`, a table of 20 small situational scoring functions (one
per node id — hand-written and bounded is right-sized here since the wheel
is a fixed, engine-owned set of exactly 20 nodes content authors never
extend, unlike chips) plus an additive `techIdentityWeight` that tilts
scores by the faction dial instead of hard-excluding 3 of 4 paths.
Confirmed in a real AI-vs-AI game (seed 777): `plainers` maxed Military's
B-branch, then correctly spent its 4th point on `eco-entry` instead of
losing it — exactly the scenario the old code stranded.

**Still open:**

- **Build (chip) scoring is a hand-tuned heuristic**, not the generic
  effect→value table the overhaul plan calls for. It mostly works today
  because current content sticks to a handful of known fields, but it's not
  robust to new chip effects (movement, influence, vision, detection,
  loyalty-rate chips still score 0 / get ignored in `pickBuild`). The tech
  side of this same concern is now resolved (above) — what's left is
  specifically the *chip* build scorer, which faces the open-ended-content
  problem the tech fix didn't have to.

**Recommended next step:** the full effect→value table rewrite
(`docs/ai-overhaul-plan.md`'s "shared evaluation core") is the remaining
bigger lift, scoped to chip/build scoring now — worth doing once new chip
content starts landing with effect types the current scorer can't see.

**Related hygiene fix, same day:** `recon-team` had the identical
id-hardcode problem as `training-grounds` (three copies of "count chips
with this literal id" — `encounters.js`, and a duplicate in
`Prototype.jsx`'s UI code), for the same underlying mechanic class
(a chip granting an encounter redraw). Generalized the same way: a
`encounterRedraws` schema field, one exported `encounterRedrawBudget(state,
pid)` in `encounters.js` that both the engine and the UI now call instead
of each re-deriving it. Worth grepping for `chipId ===` /
`locationId ===` occasionally — content.js's own header says the engine
never branches on content ids, and two real violations turned up in one
sitting once someone went looking.

### 4. Touch / iPad support — done (2026-08-07)

The prototype was mouse-only outside of `BoardViewport`'s pan (which
already used Pointer Events). Added:

- **The tech wheel's tap-to-preview / tap-to-confirm.** `TechWheel.jsx`'s
  `Segment` used to arm its info preview on `onMouseEnter` and assign on
  `onClick`. On a real touch device this broke in a genuinely subtle way,
  not just "no hover exists": mobile Safari/Chrome *synthesize*
  mouseenter→mouseleave→click around every tap (so CSS `:hover` can flash
  and clear), and all three fire in one browser task before React
  re-renders in between — so the synthesized mouseleave un-armed the
  preview before the click handler's own render ever saw it armed. Fixed
  by switching to `onPointerEnter`/`onPointerLeave` filtered to
  `pointerType === "mouse"` (Pointer Events carry the true origin device,
  unlike synthetic MouseEvents) — touch now arms/confirms purely through
  two separate `onClick` calls, which are genuinely separate events.
  Verified live in a real browser (Playwright, iPad viewport + CDP
  multi-touch dispatch, not just code review): tap 1 shows the info strip
  without assigning, tap 2 on the same segment assigns; mouse hover+click
  behavior is unchanged (verified side by side in the same test run).
- **Board pinch-to-zoom.** `BoardViewport.jsx` already panned via unified
  Pointer Events but only zoomed via mouse wheel — unreachable by touch
  (Safari doesn't synthesize `wheel` from a pinch). Added 2-pointer
  tracking to the existing `onPointerDown/Move/Up` handlers: a 2nd finger
  hands off from single-finger pan to pinch (incremental scale + pan
  toward the midpoint each frame, same math family as the existing wheel-
  zoom); lifting to 1 finger resumes panning from wherever it left off
  instead of a dead zone. Mouse is untouched (mouse only ever produces one
  pointer, so the whole branch is unreachable for it). Verified via CDP
  `Input.dispatchTouchEvent` two-finger gestures: pinch-out hit
  `MAX_SCALE`, pinch-in hit `MIN_SCALE`, and a single-finger pan
  immediately after tracked the drag delta exactly.
- **Chip and garrison tooltips** (`Chip.jsx`, `GarrisonValue.jsx`) were
  hover-only with no click-through action at all, so they were simply
  invisible on touch — you couldn't see a chip's effect text on an iPad.
  Added `useTapTooltip` (new shared hook, `kit.jsx`) so tapping toggles the
  same popover hover shows, with tap-outside-to-close (mirrors the
  editor's `HelpTip` tap-popover pattern). Mouse hover is unchanged.
- **`index.html` viewport meta** — added `maximum-scale=1, user-scalable=no`
  so iOS Safari's native double-tap-zoom/pinch-zoom-the-page doesn't fight
  the board's own pinch-zoom or the tech wheel's tap-tap pattern.
- **Deployment** — no work needed here: `.github/workflows/pages.yml`
  already auto-deploys every push to `main` to
  `https://lazmcspaz.github.io/PABC/`, confirmed live via the Actions
  history. That's the URL to test from an iPad — nothing needs to run
  locally.

**Known remaining gap, not yet fixed:** `SalvageModal.jsx`'s chip-pickup
uses HTML5 drag-and-drop (`draggable`, `onDragStart/onDragOver/onDrop`),
which has no equivalent on iOS Safari touch at all — salvage-chip
assignment after a kill will not work on an iPad today. Fixing it means
rewriting that interaction as pointer-based drag (reusing the same
Pointer Events pattern as `BoardViewport`'s pan), not a small tweak —
flagged here rather than done silently since it wasn't explicitly in
scope for this pass.

### 5. Fixed a real bug — self-contest (2026-08-08)

User-reported: a player could "contest" their own fully-controlled
Location with their own unit. Root cause was structural, in
`contest.js`'s `flipSection` — `loc.controller` was only ever **set**
(via `captureLocation`, once a player reaches full 3/3 control) and never
**cleared** when a player *lost* a section short of losing all three. So
a Location that dropped from 3/3 to 2/3 kept reading as "fully controlled
by the old owner" everywhere `loc.controller` is checked — income
collection, build/upgrade rights, passive heal eligibility, ZoC/movement
blocking, and contest eligibility. The visible symptom: the old owner's
own unit, standing on its own partially-lost Location, could "contest"
it — and `defenderValue()` folded that *same* unit's Strength in as the
defense, since it stacks `loc.controller`'s units on the hex and
`loc.controller` was still (wrongly) the attacker.

Fix mirrors what `turn.js`'s Loyalty-decay peel already did on the same
condition (that path was correct — decay clears `loc.controller` when a
peel drops it below full control) — applied to the contest-loss path,
which didn't have it. One side effect required a second fix:
`captureLocation`'s "captured FROM" attribution read `loc.controller` at
capture time, which — now that it clears immediately on partial loss —
is always `null` by the time a full capture completes via the contest
path. Fixed by falling back to `loc.loyaltyOwner`, which (correctly)
survives a *partial* loss and only clears once a Location decays fully to
neutral — it's the right "who was this taken from" memory through a
partial-control interim.

**Second-order effect worth knowing about:** fixing this closed a
loophole that had been propping up AI conquest pace — a faction that lost
one section of a Location no longer keeps collecting its income/build/
heal rights while contesting stays blocked. One existing harness check
(`[AI sanity] a full AI-vs-AI game terminates with a winner`, hardcoded to
seed 42) started failing after the fix — not from an infinite loop or any
new bug (verified: turns keep completing, locations keep changing hands,
VP keeps being awarded), but because seed 42 specifically settles into a
genuine 4-way stalemate post-fix and no longer snowballs to a winner
within the test's turn budget. 6 other seeds tried all still converge
comfortably. Swapped the test to seed 5, which does — the check exists to
catch a true engine hang, not to assert every seed's emergent AI dynamics
must converge to a winner in a fixed budget. Worth knowing: **the AI may
now be more prone to stalemates than before**, since it can no longer
lean on the bug's artificial stability. Not fixed here — would fall under
the "AI quality" bucket above (something like: prioritize consolidating/
defending a freshly-partial-lost Location over opening a new front) if it
turns out to matter in practice.

Verified with a harness regression test using an unambiguous fixture
(every other unit deliberately moved off the contested hex, not scored by
hand) proving both the immediate bug (self-referential defense value) and
the second-order fix (correct capture attribution). Clean across a
200-seed sweep; `npm run build` succeeds.

### 6. Fixed a real bug — +1 Movement tech not reaching units, plus a
full exportable playtest log (2026-08-07)

User-reported: taking the Logistics tech node that grants +1 Movement
didn't change how far units could actually move. Root cause: a unit
carries two related fields — `movement` (the current cap, recomputed
whenever tech/modifiers change) and `moveRemaining` (the turn's *usable*
budget, which only resets once per Upkeep). `recomputeStats()` correctly
bumped `movement` the instant the tech was assigned, but nothing told
`moveRemaining` to grow with it — so a unit that had already moved (or
even one that hadn't) kept its stale pre-tech budget until its next
Upkeep refresh. Fixed by tracking each unit's movement delta inside
`recomputeStats()` and applying the same delta to `moveRemaining`,
clamped to `[0, newMovement]` — a unit that hasn't moved yet gets the
full new cap immediately, one that's already spent some budget this turn
gets the difference added on top rather than being reset. Verified with
two new harness checks (untouched budget and partially-spent budget both
extend correctly) plus the full 280-check suite and a 200-seed sweep.

Separately, to make bugs like both of these *findable* without needing an
engineering session per report, added a full **playtest log export**
(Settings → "Export Playtest Log"). `state.log` already recorded every
`emit()` in the engine chronologically; `EventFeed.jsx` only ever showed
a curated, truncated live view (last 14 lines, ~20 event types
suppressed as HUD noise). The new `src/prototype/gameLogExport.js`
renders the *entire* uncurated log as a human-readable transcript and
triggers a browser download (`Blob` + object URL, no server involved) —
covering roughly 85 distinct event types, each spelling out the numbers
behind it (dice rolls, modifiers, margins, movement caps vs. remaining,
tech effect text, diplomacy terms) rather than summarizing, since the
point is to let a read-through catch a mismatch between what should have
happened and what did.

Two things worth knowing for anyone extending it:
- **Every formatter was cross-checked against real `emit()` payloads**,
  not written from memory of what a field is probably called — a Python
  script extracted every `emit(state, "name", {...})` call site across
  `src/game/*.js` and diffed it against the formatter's field usage,
  catching upwards of 15 wrong-field-name bugs before they shipped
  (worst one: `contest_won`/`contest_lost` formatters referencing
  `margin`/`killed`/attrition fields that only exist on `performAction`'s
  *return value*, never on the logged event itself — fixed by computing
  margin locally from the fields the event actually carries).
- **Formatters run once, at export time, against final game state** —
  not against "state as it was when the event fired." That's safe for
  most fields (contest payloads already bake in every number at
  resolution time; location/chip/tech names are static all game). It is
  *not* safe for a unit's live, mutable stats — reading
  `state.units[p.unit].moveRemaining` for a historical `unit_moved` line
  would show that unit's *final* stats against every move it ever made,
  or blow up entirely once the unit dies. Fixed by snapshotting
  point-in-time facts (`player`, `movement`, `moveRemaining`) directly
  into the `unit_moved`/`unit_retreated`/`loot_claimed` emit payloads in
  `actions.js`/`contest.js`, rather than reconstructing history from
  final state in the formatter. Any new formatter needing a mutable fact
  should follow that pattern, not read `state` live.

Verified end-to-end with Playwright: launched the app, played several
real turns (human move + AI turns via End Turn), exported the log, and
inspected the actual downloaded file — 773 events, correct per-faction/
per-location summaries, movement lines showing cap and remaining
budget, contest lines showing full dice/modifier breakdowns, zero
`undefined`/`NaN` leaks anywhere in the text. Harness (280/280) and
`npm run build` (508 modules) both clean.

### 7. Phone-width layout — core gameplay screens (2026-08-07)

User-reported: the game looked right on an iPad but broke on a phone.
Root cause: the entire UI had exactly zero responsive breakpoints — every
HUD cluster, modal, and the tech/radial wheels used fixed pixel
geometry sized for ≥700px. Confirmed via Playwright at 390×844
(iPhone-class) and eyeballed down to 360px (small-Android floor agreed
with the user): the top HUD bar's three independently-positioned
clusters (resources, faction name, VP/Actions dials) physically
collided into unreadable overlapping text; the Tech Wheel (a fixed
480×480 SVG) and the Radial Menu (a fixed 460×460 SVG) both overflowed
a 390px screen outright; `UnitPanel` (fixed 440px, two-column) and
`FrameWindow`-based modals (`LocationWindow`/`TitledWindow`, default
470px) ran off the right edge.

Scope agreed with the user: fix the core gameplay screens now (the
board + HUD + the panels/menus you touch constantly while playing);
defer the title screen, setup/configure-match screen, and a from-scratch
Diplomacy Drawer redesign to a fast-follow pass — those still render
their existing desktop layout unchanged, cropped rather than reflowed on
a phone.

Added one shared piece of infrastructure — `useViewport.js`
(`useViewportSize`/`useIsPhone`, threshold 480px) — and used it to add a
phone-specific path alongside each existing desktop layout, never
replacing it:

- **TopBar** (`HudChrome.jsx`) — the flared multi-cluster desktop bar is
  unchanged above 480px; below it, `CompactTopBar` renders a plain
  three-row bar (faction/settings, a row of 5 icon+value stat chips,
  full-width End Turn) at a fixed, deterministic height
  (`COMPACT_HUD_H`) so sibling components can offset below it without
  measuring the DOM.
- **BoardViewport**'s zoom cluster and **EventFeed** both take the
  compact HUD height as an offset from `Prototype.jsx` so they sit below
  the phone bar instead of underneath it; EventFeed also narrows and
  shrinks its max height on phone.
- **RadialMenu** and **TechWheel** — both were fixed-size SVGs assuming
  ≥460-480px of space with zero notion of viewport size. Both now derive
  a scale factor `k` from `min(baseSize, vw*0.9-ish, vh*0.6-0.7-ish)` and
  multiply every radius/icon/gap by it (TechWheel floors label/icon
  scale at 0.8× so text stays legible even fully shrunk). Threaded `k`
  and the derived ring geometry through `Segment`/`SegmentContent` as a
  `geo` prop rather than the module-level constants they used to close
  over.
- **UnitPanel** — switches from the fixed 440px two-column (stats |
  divider | tags/actions) layout to a full-width, single-column stacked
  layout on phone (horizontal divider instead of vertical); raises its
  `bottom` offset on phone so the taller stacked panel still clears the
  bottom-right MenuOrb instead of covering it.
- **FrameWindow** (`LocationWindow`/`TitledWindow`, and anything else
  built on it) — added `maxWidth: "94vw"` next to its fixed `width`, the
  same pattern `Inspector.jsx`'s modal already used. One-line, zero
  behavior change above 94vw, and it's what makes the Location window —
  the single most-used interaction in the game — render correctly on
  phone at all.
- **DiplomacyDrawer** — safety-only pass, not a redesign: capped the
  main drawer (`width: 420`) and its `ConfirmDialog` (`width: 340`) with
  `maxWidth` so neither runs off-screen. The deal-builder/tribute/peace
  sub-panes still assume desktop width internally; a real phone layout
  for Diplomacy is part of the deferred fast-follow.

Verified with Playwright at 390×844 (phone) and 1024×768 (tablet, to
confirm zero regression above the breakpoint): board/HUD, unit
selection/UnitPanel, the Radial Menu, the Tech Wheel, and the Location
window all render fully on-screen with no overlap or clipping on phone,
and are pixel-identical in structure to before this change at tablet
width. Harness (280/280) and `npm run build` (509 modules) both clean.

**Still phone-broken, by agreed scope** (fast-follow, not silently
fixed): the setup/configure-match screen (a fixed two-column grid whose
Map Size row and Victory Conditions text run off the right edge) still
renders its original desktop layout, just cropped; and DiplomacyDrawer's
inner sub-panes (deal builder etc.), which got only the overflow-safety
patch above, not a real compact layout. (The title screen — originally
in this deferred list too — was fixed in §8 below after the user hit it

### 8. Fixed two more real bugs — faction-portrait cropping and the
title screen clipping its own menu (2026-08-07)

User-reported, with a real-phone screenshot: the faction-select
portraits had black bars down the sides instead of filling their
frame, and the title screen (reported as "still needs work" after §7)
was overflowing on the user's phone.

**Portrait cropping** — `FactionCard`'s `<img>` in `SetupScreen.jsx`
only had `height: "100%"` set; `width` fell back to `auto`. `objectFit:
"cover"` needs *both* axes constrained to actually crop into a box —
with only one axis fixed, the browser just scales the image to that
height at its native aspect ratio and leaves whatever gap is left over
on the other axis, which reads as black bars. All four portraits are
816×1232, taller than the card's content box, so every card showed
pillarboxing on the sides. Fixed by setting `width: "100%"` alongside
`height: "100%"` — the same fix, applied along the way: the currently-
selected card's portrait now gets a slow (9s), subtle scale-breathe via
a `portrait-slow-zoom` keyframe (guarded behind
`prefers-reduced-motion`, matching every other looping animation in
`prototype.css`) so the setup screen has a touch of life to it.

**Title screen** — this was flagged as deferred/phone-broken in §7, but
the user's screenshot showed something worse than cosmetic overflow:
the entire right-hand menu column (New Game, Continue, Load Game, Lore,
Settings) was clipped clean off the screen by the page's
`overflow: hidden`, not just visually cropped — on a phone there was no
way to reach the menu at all. Root cause turned out to be two separate
bugs stacked on each other:

1. The outer content row had a *fixed* `width: 1100` with no per-column
   width discipline — the left column (`flex: "0 0 auto"`) had no width
   constraint of its own, so the one-line "ASHLAND CONQUEST" title (at
   its 62px font, one continuous line renders ~820px wide) plus the
   menu column's `minWidth: 320` plus the 56px gap between them added
   up to more than the 1100px container at *any* viewport, phone or not
   — confirmed by reproducing the exact same clipped-menu screenshot on
   the unmodified code at a plain 1280px desktop width, so this half of
   the bug predates the phone work entirely and just hadn't been
   noticed yet.
2. On top of that, phones don't have the ~1100px of layout room the
   fixed-width row assumed at all.

Fixed both at once: gave the left column a `maxWidth: 460` (desktop) so
"Ashland" and "Conquest" — already two separate inline pieces in the
markup — wrap onto their own lines instead of forcing one very wide
line, which frees enough width for the menu column at every desktop/
tablet size without changing the row's fixed-width design. On phone
(`useIsPhone`), the row switches to a stacked column layout instead
(title block, then the splash placeholder scaled to the column width,
then the menu panel full-width beneath), with responsive type sizes
throughout and `maxHeight: 94vh` + internal scroll as a backstop against
very short screens.

Verified with Playwright across six widths in one pass (360, 390, 768,
1024, 1280, 1440) — at every one, every menu item's bounding box is
fully within the viewport and clickable, screenshotted for a visual
check at each. Harness (280/280) and `npm run build` both clean.

### 9. Setup screen phone layout, plus a smaller UnitPanel and a shorter
event log (2026-08-07)

User-reported, with a real-phone screenshot: the configure-match screen
was still using its fixed `1fr 340px` two-column grid on phone — with
no width to spare, the "1fr" faction column got squeezed down to ~30px-
wide portrait slivers, and the "340px" settings column pushed itself
half off-screen (Map Size's "Large"/"Huge" options and the Victory
Conditions descriptions ran off the right edge). Fixed by switching to
a single stacked column on phone: `gridTemplateColumns: "1fr"`, the
faction grid drops from 4 columns to 2 (portraits render at a normal,
recognizable size), and the Begin row stacks its summary text above a
full-width button instead of squeezing both onto one row. The user
explicitly said scrolling to see the rest is fine, so no attempt was
made to fit everything above the fold — the page already scrolled
(`overflow: auto` was already there), it just needed the grid to stop
being wider than the screen.

Separately, two rounds of screenshots from a real phone showed the
`UnitPanel` (opened on every unit tap) and `EventFeed` eating close to
half the visible board. `EventFeed`'s phone `maxHeight` dropped from
190 to 130. `UnitPanel` got a real redesign for phone rather than a
font-size trim: the three stat readouts (Strength/Moves/Status) were
each their own icon-above-value-above-label *column* — correct for the
side-by-side desktop layout, but three stacked columns is what made the
phone version tall once it switched to a single-column body. Added
`PhoneStatChip`, which puts icon + value + label inline in one row, and
used three of those side by side instead — same information, roughly a
third the vertical space. Chip Bay slot height and every other padding/

the pre-fix screenshot at the same viewport: panel height dropped from
~275px to ~165px (a little over 40%), with the desktop/tablet layout
(which uses the original `StatCell` unchanged) byte-for-byte the same
render as before.

Verified with Playwright at 390×844 (setup screen scroll-through, unit
panel, event log) and 1280×900 (confirming zero change to desktop/
tablet). Harness (280/280) and `npm run build` both clean.

## Suggested sequencing

Unlike the v0.2 roadmap, these three buckets are **not** dependent on each
other — they can run fully in parallel:

```
AI quality (ai.js only)         ─┐
Content authoring (editor + CSVs) ─┼─► converge whenever, no shared files
Legacy cleanup + art             ─┘
```

- **Content authoring** has the best ratio of "amount left" to "no
  engineering risk" — it's the natural place to put the most hours right
  now, and multiple people can author in parallel (quests, world
  encounters, chips, locations, tuning tables are all independent files/
  tables in the editor).
- **AI EV-gating for contests** is the highest-value engineering fix if you
  want the AI to *feel* smart while content is being authored — small,
  contained to `ai.js` + reading existing `contest.js` math, no schema
  changes.
- **Art** has no dependencies and can happen whenever someone has spare
  time. (Legacy removal — the other item in this bucket — is done.)

## Guardrails (carried over, still apply)

- Never hand-edit `content/` or `src/game/content/` — the editor tool owns
  them; author through it.
- Verify with `node src/game/harness.js` before calling any engine change
  done; it's cheap and catches regressions across every system at once.
- `src/prototype/engineAdapter.js` remains the only seam between the engine
  and the React UI.
